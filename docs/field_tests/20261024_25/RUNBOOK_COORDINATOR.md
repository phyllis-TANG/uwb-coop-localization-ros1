# C端：协调、配置与评价口径任务书

当前窗口承担单一协调者角色。先读[README](README.md)、[EXPERIMENTS](EXPERIMENTS.md)、[QC_REPORT](QC_REPORT.md)和[RESULT_CONTRACT](RESULT_CONTRACT.md)，再看需要核对的[历史记录](SESSION_LOG_ARCHIVE.md)。协调不代表自动控制其他窗口；三个端必须通过共同提交、输入SHA和明确产物交接。

## C1：在交接PR合并后发布共同起点

只读检查工作区、分支、远端、最新提交；不要对包含他人工作的检出直接pull/reset。使用干净main检出确认本交接目录与工具已合入：

```bash
pwd
git status --short --branch
git branch --show-current
git remote -v
git log -5 --oneline
```

仅在观察到工作区干净、当前main、远端地址正确时执行：

```bash
git pull --ff-only origin main
git rev-parse HEAD
sha256sum docs/field_tests/20261024_25/manifest.json docs/field_tests/20261024_25/geometry.json
```

将实际HEAD作为本轮`HANDOFF_COMMIT`发给A/B端，附上两个配置摘要。三个端都应回报检出HEAD、Python/工具版本、数据身份和任务分支。旧基线`f14f8bd...`不包含本交接新增工具，不能当合并后的作业版本。

协调端自己的更改放在独立分支，例如`docs/field-coordination-20261026-<标识>`。`manifest.json`、`geometry.json`和实验表只由协调者更新；A/B端建议变更而不同时直接改它们。每次公共配置变更均递增/记录版本与来源，通知依赖端；旧结果保留，不在原运行目录重写。

## C2：维护输入、未知项与文件身份

按实际到达的Release附件更新清单，不只看用户口述或ZIP名。对于新增T11–T15视频，需记录实际名称、大小、SHA、原MOV身份、完整解码及实验对应；不能把“等待上传”提前标DONE。原文件留在Release/外部数据存储，仓库只存清单、紧凑证据与代码。

当前T11/T12/T13视频ZIP已在Release，状态仅为“已上传、内容验收待做”；T14/T15视频仍未到达。将新增三包的下载/CRC/解码任务交给B端，不要把它们混写为此前已完整检查的T08–T10。

当前需要后续澄清的项目：

- Car2运动日志尚未在现有归档中找到。
- T14/T15实际遮挡材料、实体位置、进入/撤离时段及对象，不能凭指导方案假定node10链路已有效遮挡。
- P点实际尺量确认、Q点实际摆位/高度与八段参考片逐一对应。
- Car2板倾角未测、画面弯曲与标记提取影响；Car1/Car2安装是否与每条正式片一致。
- T12实际初始完整几何未知；起始中心距最终确认2.00m。T13复位坐标及2.12m起距已确认。T10的1.75m起距是沿用T09末读数，不是新测量。

缺项只阻塞受其影响的结论，不阻塞全部只读诊断。不要求用户在已经拆场后反造精确事件或为无关项立即重新录制。

## C3：并行工作与评价冻结

先让A端完成bag复核/标准化与时间诊断，B端完成视觉提取/参考验证。A端可在等待B端时实现接口及合成测试，但不使用未批准的视觉参考调定位误差。

在看留出定位误差前，形成一次明确的评价批准记录，至少包含：

- `HANDOFF_COMMIT`、后续方法源码提交/哈希、manifest与geometry摘要。
- 参考产物SHA、空间与时间适用范围，连续轨迹或仅停点。
- 运行包划分：开发T08/T10/T12/T14；留出T09/T11/T13/T15，整包不随机拆帧。
- Odom-only、独立UWB/Odom、固定peer联合解的统一输入、初始化/对齐规则、可用锚点、外参、时间基准、求解因果性和评价窗口。
- 待比较指标与失败标准、参考有效帧规则、遮挡时段如何取得及其近似边界。

未知参考精度时不能预设“厘米级”；若只能验证停点，则只批准停点评价。算法估计与独立参考的对齐规则不能每包按终点反求。候选机制及消融应在开发诊断支持后确定，不提前规定必须得到正向结果或固定文章标题。

## C4：合并各端结果

按下列顺序检查每个端的PR/产物：

1. 运行来源：代码/配置/输入/参考哈希是否一致，环境和命令是否可复现。
2. 实际状态：DONE、BLOCKED、FAILED是否有证据；原始数据是否未修改。
3. 单位、时钟域、frame、无效/未知字段是否按统一契约，不误用Car2 odom.z、NaN quality或接收时间差。
4. 文件健康、方法测试、实际输出计数是否通过；报告是否区分Odom反馈与地面运动。
5. 参考适用范围、留出边界和人工读数修正是否被保留；是否出现参考反调、测试调参、终点因子等泄漏。
6. 仅合并本端拥有的代码和紧凑结果；大视频、bag、环境缓存与绝对本机路径不进入代码PR。

使用独立分支和PR，不让三个端同时修改公共配置或主文件。不代用户自动合并。合并后如需要继续并行，发布新的共同提交或明确旧结果的源码锁，不能让各端默认追随不断移动的main。

## C5：研究结论与最终产物

保留旧包及弱效/无效退化试验。每个方法同时报告成功、失败、无改进和适用限制，不按结果挑包。50Hz帧不等于大量独立实验，至少以整次运行呈现重复差异。

最终汇总应先回答平台/参考是否可靠、退化是否存在、各固定基线表现，再决定候选机制能否解释并改善数据。月球背景可以保留为动机或未来外推，不把室内实验包装成已验证月面性能；标题在结果和方法明确后确定。

对其他端可直接使用[PROMPTS.md](PROMPTS.md)。需要夜间任务时使用[NIGHTLY_SANDBOX.md](NIGHTLY_SANDBOX.md)规定的有限计划和恢复方式；不要承诺关闭窗口后所有平台都会继续执行，也不要擅自扩大授权到真实机器人、账户权限或自动合并。
