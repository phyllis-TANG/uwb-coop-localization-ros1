## Car1已经得到的信号级证据

对同一台车按2ms最近header进行离线一对一配对，再在相邻正向、≤100ms有效间隔检查：

- odom yaw步进是否符合其自己报告的angular_z乘以源header间隔；
- odom XY步进是否符合当前body线速度经上一步odom yaw旋转后积分；
- IMU与odom相对yaw变化是否同一条序列。

| Car1数据 | 配对数 | 自身角速度积分单步残差RMS(rad) | 自身线速度积分单步残差RMS(m) | IMU−odom相对yaw差的跨度(°) |
| --- | ---: | ---: | ---: | ---: |
| 10/18键盘返回 | 1654 | 1.25e-08 | 1.01e-07 | 11.40 |
| 10/18首次同动 | 2310 | 4.3e-09 | 3.78e-08 | 10.48 |
| T08 | 4879 | 0 | 0 | 11.02 |
| T10 | 1161 | 1.51e-08 | 5.65e-08 | 8.04 |

**表中很小的单步残差是消息之间的数值一致性，绝不是纳米级位置或高精度航向。** 源header是发布时钟，未被标定为硬件采样时刻。IMU−odom差的跨度也不是真实角误差。

Car1在旧动态包与T10中高度符合“对发布的底盘速度作积分”的输出关系；它与IMU已发布姿态的相对变化不同，原始gyro逐步积分的残差也明显不同。这排除了最简单的“把当前发布的IMU姿态/未补偿gyro原样复制成odom”的解释，支持选择替换角运动输入的离线模型。

但不能据此声称：odom是纯编码器、MCU完全没用gyro、两路统计独立、IMU/body安装旋转已标定。底层可以使用补偿、门限或其他融合，再输出同样的数据关系；被动bag无法唯一辨识这些内部实现。

八组车流的连接记录中，odom/imu发布者均为相应的/car1/wheeltec_robot或/car2/wheeltec_robot。它支持所记录消息来自底盘节点；一个robot_pose_ekf.launch文件存在，不证明bag里已经消费了其输出。

## 现在就可以开始的路线

1. 保留原UWB/Odom三基线及PR54可靠性结果，另建默认关闭的IMU模式。
2. 用同车odom.twist的车体线速度和原始gyro_z−bias作运动传播，明确替换旧odom yaw/角增量，不再将其与IMU姿态作为多份独立航向约束叠加。上游速度可能与gyro相关仍需声明，工程协方差不解释为已标定后验。
3. 增加每车gyro零偏状态，采用实际源时间间隔、过期/缺口拒绝及恢复策略。数据中的5秒命令安静候选只作有条件诊断，不自动批准物理静止、初值或噪声标定。
4. IMU→body的平面Z轴约定、时间映射和零偏初始先明确为配置/工程假设，做单独敏感性；不借终点或未验收视觉挑选最好者。Car1现有小转角不能替代完整安装旋转标定。
5. 先在合成测试验证偏置状态、异步输入、缺口和回退，再用T08/T10开发包跑原基线对照。暂不做加速度双积分，不将厂商四元数当房间绝对yaw；不打开留出包。
